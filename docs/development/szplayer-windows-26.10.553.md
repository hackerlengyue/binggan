# Windows SZPlayer 26.10.553：采集与解密

[开发指南](README.md#windows未进行测试) · [文档导航](../README.md)

本文记录对 `SZPlayer_26.10.553_Analysis` 的核对结果，以及 Binggan 的 Windows 适配范围。文件容器解密使用 Go 实现；sing-box 负责流量路由，本地代理负责 HTTPS 解密。两者使用不同参数。

## 材料与证据边界

分析包包含 4 份报告、提取的字符串与引用、55 个分析脚本、REA 证据和 IDA 数据库。多数脚本读取原作者 Windows 路径下的二进制，不能在本项目中直接运行。未将脚本或数据库作为应用运行依赖。

报告标识的目标为 32 位 Qt 5.9.1 程序 `MainPlayer.exe`，SHA-256 为 `fd2d8f5938ae25b9f3bfbd2cd255d6f0674376774118196a2fced5b26f705fd4`。这是报告提供的目标标识，本次未用原始 EXE 独立复核。

本次主要核对的本地报告：

| 文件 | SHA-256 |
| --- | --- |
| `01_报告/SZPlayer视频格式全集.md` | `e562f9c780a5c80897a838e8facf80ba208090621e8d229920023acf5ec4b83b` |
| `01_报告/SZPlayer完整逆向分析文档.md` | `f59604a60bb4491657a69550443ee63645ab81ba53d91beb0a6f174e1de12cef` |
| `密钥派生链-最终结论与验证.md`（后续补充） | `48a714f2ba7b9175cb535551cd745f0d9f7b60385b0aea188eab78ebe15afe2e` |

报告中以下限制直接影响实现：

- 第一版附录 Python 中的 K1/K2 零值是占位符。后续补充报告提出 `K1=K2=1`（小端 `01 00 00 00`），并提供派生向量；本次按该假设接入可选择的实验模式，尚未用真实播放器样本确认。
- 后续补充报告撤回了「空哈希退化、Key 恒定」的结论，改为文件名参与派生。旧结论不应继续用于实现。
- 「填充值等于指针低字节重复 16 次」的解释仍需复核。补充报告同时出现从指针读取和使用指针数值的说法，不能据此断言只有 256 种可能。
- 326 的伪代码从盐区派生 IV，附带 Python 则从中间摘要派生 IV，两者不一致。分片能否直接拼接成一个媒体文件也没有实测样本证明。
- 较早的完整报告将部分常量标为 `SZPDF`；视频专项报告的第 0、12 节对此有修正。582 是 `0x246`，文件开头会出现 `53 5A 50 44 46 02 00 00`。前五字节虽然显示为 `SZPDF`，实际应按 `SZPD` 加小端版本号 582 识别。
- `softwareName` 的实际 Windows 字面值、第二个动态请求头和部分元数据字段仍未确认。PE 文件版本不能直接充当请求参数。

## 当前能力

| 部分 | 当前处理 |
| --- | --- |
| 播放器发现 | 支持运行进程、32/64 位注册表视图、常用便携目录和显式路径；可识别 `MainPlayer.exe`。 |
| 流量路由 | 匹配 SzPlayer 进程名、受限的 SZPlayer 安装路径及发现的实际路径。普通 `MainPlayer.exe` 不会仅因名称相同而被接管。 |
| HTTPS 采集 | 通过本地认证 SOCKS 中继和代理保留请求/响应；支持目标域名及备用子域名。 |
| Windows 系统处理 | TUN 使用 `BingganCapture` 网卡名；管理员授权被取消时返回可操作提示；证书安装状态通过 CryptoAPI 检查当前用户存储。 |
| SZPD 582 | 支持真实 AES Key/IV，也可显式选择实验性的文件名派生；流式解密、严格校验 PKCS#7 与明文长度、封装 MP4、完整解码后发布结果。 |
| SZPD 326 / 其他版本 | 创建任务时识别并拒绝，显示版本及待验证提示。 |
| 原有 MP4 采样加密 | 保留既有密钥格式与处理流程；与 SZPD 密钥互用时给出格式错误。 |
| 播放编排 | Windows 原生控件驱动尚未实现，需手动在播放器中打开课程。 |

32 位播放器可由 x64 或 ARM64 Binggan 通过系统进程接口发现。Binggan 和 FFmpeg 资源仍需按运行环境选取；播放器的位数不决定应用的构建目标。

## Windows 采集流程

1. 解压完整的 Binggan 构建产物，保留随包工具；确认系统有 WebView2 运行环境。
2. 使用日常账户启动 Binggan，在「证书管理」安装并信任当前 CA。安装写入当前用户的 `CA` 存储，信任写入当前用户的 `Root` 存储。
3. 在流量接管的 Windows 管理员授权窗口中允许启动辅助进程。辅助进程负责 TUN，桌面窗口与证书操作继续使用原账户。
4. 打开深造播放器，再开始采集并手动播放一个课程。安装证书前已打开的播放器可先退出，再重新打开。
5. 确认请求列表中同时出现请求和响应，再结束并保存采集记录。

便携目录未被发现时，在启动 Binggan 前指定路径。例如 PowerShell：

```powershell
$env:SZJM_PLAYER_PATH = 'D:\学习软件\SZPlayer 26.10.553\MainPlayer.exe'
& '.\饼干大小姐.exe'
```

默认 API 地址为报告中的 `https://video.shenzaokeji.com`，备用线路仍位于 `*.shenzaokeji.com`。已知接口包括：

| 接口 | 报告中的参数或返回内容 |
| --- | --- |
| `/api/cloud-course/getCourseMd5` | `courseNo`；返回 `encryptionMd5`、`videoMd5`。 |
| `/api/courseLocal/getPwd3V2` | 请求含 `den`、`dts`、`num`、`encryptionMd5`、`softMd5`；返回 `data.pwd`，报告称播放调用取前 8 字符。 |
| `/api/courseLocal/getPerinutePwd` | 请求含 `encryptionMd5`、`userId`、`softMd5`；返回结构可能含 `pwd_Audio`、`Audio_start`。 |

采集保留原始响应，不会把前 8 字符、`pwd_Audio` 或 `softMd5` 自动当作容器 AES Key/IV。Windows 接口记录也不保证满足 macOS 的密钥 JSON 格式。原始记录可以保存用于后续核对。

sing-box 支持 Windows 的进程路径路由。本项目保持 `strict_route=false`、`dns_mode=disabled`；官方文档说明 Windows 的严格路由会影响其他接口上的 DNS，因此这里没有启用它。[路由规则](https://sing-box.sagernet.org/configuration/route/rule/) · [TUN 配置](https://sing-box.sagernet.org/configuration/inbound/tun/)

当前锁定的 sing-tun 源码为 x64、ARM64 内嵌了对应的 Wintun DLL，不需要另行下载到播放器目录。依据是 Go module 中的 `internal/wintun/dll_windows_amd64.go`、`dll_windows_arm64.go`。

## SZPD 582 文件解密

可选择真实 AES 参数或补充报告提出的实验性派生方案。两种方式均用于本人拥有或已获授权的文件。IV 不能直接填写文件头的 salt；它们是不同的量。

### 使用真实 AES 参数

前提：已取得与源文件对应的 32 字节 AES Key 和 16 字节 IV。

密钥 JSON 结构如下，尖括号内容必须替换为真实十六进制参数：

```json
{
  "passwords": {},
  "getPwdData": {
    "pattern": "szpd",
    "aesKey": "<32字节Key，64个十六进制字符>",
    "aesIV": "<16字节IV，32个十六进制字符>"
  }
}
```

1. 在「密钥管理」上传 JSON。
2. 在「视频解密」导入对应 `.sz` 文件并选择该密钥。
3. 创建任务，等待解密、MP4 封装和最终校验完成。
4. 在「资源管理」查看生成的 MP4。

此模式不需要 `uit`、`appMd5` 或 macOS 播放器。缺失的传统数字参数在前端导入时补为 0。Key/IV 会随密钥记录保存到本地，应按密钥文件管理。

引擎读取 `+0x0C` 明文长度、`+0x10` 密文长度以及从 `+0x24` 开始的密文，以固定内存分块解密。它检查密文边界、16 字节对齐、PKCS#7 填充及明文长度；不会把填充错误当成无填充数据继续处理。明文媒体通过 FFmpeg 复制音视频流封装到 MP4，再做完整媒体解码。MP4 不支持的编码会返回封装错误。

该分支不套用 macOS 音频频谱修复参数，也不自动处理额外的内层加密。完整解码证明输出可解码，音画内容是否正确仍需播放确认。失败或取消时清理临时目录，校验完成前不发布输出文件。

### 尝试文件名派生

在「密钥管理」导入 [派生配置 JSON](examples/szpd-filename-fill.json)，然后在视频解密任务中选择该配置：

```json
{
  "passwords": {},
  "getPwdData": {
    "pattern": "szpd",
    "derivation": "filename-fill-v1"
  }
}
```

该配置不需要手动填写 AES Key/IV。它显式启用以下假设，不会自动替换手动 AES 配置：

```text
material = SHA256(originalFileNameBytes || repeat(fillByte, 16))
key      = SHA256(material || 01 00 00 00)
iv       = SHA256(salt || 01 00 00 00)[0:16]
```

引擎枚举 `fillByte=0…255`，每个候选只检查最多 512 字节的媒体头及末尾 CBC 填充。唯一候选通过后，才完整解密并执行 MP4 封装和完整媒体解码；没有候选或存在多个候选时直接失败，不输出猜测结果。

默认文件名是所选视频的原始名称，按 UTF-8 编码，保留大小写和空格。任务入队前将原名写入任务自己的配置，防止副本被改名为 `input.sz` 后影响派生；批量任务各自保存原名，重启重试仍然使用该名称。

文件曾改名时，可在配置中加入 `fileName`，填写派生时使用的确切名称。若已知 Windows 播放器传入的是其他编码或完整路径字节，可使用 `fileNameHex` 提供确切十六进制字节。两字段互斥，配置值仅参与哈希，不会作为文件路径打开。例如 GBK 字节的「课程.sz」可填写 `"fileNameHex": "bfceb3cc2e737a"`。不能从当前文件名推断曾经使用的原名或编码。

`derivation` 模式不能同时填写 `aesKey/aesIV`。该模式不需要 `softwareName`、`softMd5` 或网络会话参数；这不等于在线播放及可能的内层加密均已验证。

### 补充报告中仍需复核的证据

- **填充语义：** `0x4E6711–0x4E671A` 展示了指针和指针加 16 的参数形态。它需要结合 `sub_4E7C90` 函数体确认，不能仅凭这些指令排除范围复制。C++ 的 `vector::insert` 同时存在重复插入和范围插入重载。[Microsoft 文档](https://learn.microsoft.com/en-us/cpp/standard-library/vector-class#insert)
- **K1 的首次来源：** `sub_4E6450` 内的 `mov ecx,1` 能支持检查后一次调用的数据流；第一次调用前的 K1 还要核对 `sub_4E6680` 的返回路径。当前将 `K1=K2=1` 视为报告提出的候选规则。
- **断点栈偏移：** 补充报告在 `call sub_4E7AC0` 前按 `[esp+4]` 读取 a5，与所列四条 `push` 的顺序不一致；应按断点位于调用前还是函数入口重新计算偏移。
- **闭环证据：** 用同一假设构造、加密、再解密自建文件，只能证明实现自洽；含 `ftyp/isom` 头也不等于完整可播放视频。真实 `.sz`、播放器对应哈希输入及音画检查仍未提供。

本项目复算出的 `lesson01.sz`、fill=0、salt=`a0…af` 的 Key 为 `0131b434f03922069d89edda14b839ca9e57a92e2d96d255649968fb1ea32962`，IV 为 `26935c2e70fda1a1fb82d2ce59bc02fe`，与补充报告 `derive_v2.py` 示例一致。测试另外覆盖了 UTF-8 中文名称、原始编码字节、256 次筛选的固定读取量、伪媒体拒绝以及批量任务重启重试。这些是实现验证，不能替代真实播放器兼容性验证。

## 排查与实机验收

| 现象 | 检查与恢复 |
| --- | --- |
| 管理员授权已取消 | 点击重新连接，再允许辅助进程启动。 |
| 找到播放器但缺少校验参数 | 已发现安装位置；PE 版本及二进制摘要尚不能证明 API 参数。SZPD 模式可使用独立 AES JSON。 |
| 没有请求记录 | 确认采集已开启、播放器路径已发现，并在接管就绪后重新打开课程。若有其他 VPN/TUN，先退出其 TUN 模式，再重试。 |
| HTTPS 握手失败 | 检查当前 CA 的指纹及系统信任，重启播放器后复试；仍失败时保留错误日志，不能据此断言播放器支持当前 CA。 |
| 提示 SZPD 582 需要 AES 参数 | 当前选择的是传统接口密钥，改用对应文件的 `szpd` JSON。 |
| 填充或长度校验失败 | 检查下载是否完整、Key/IV 是否属于该文件。 |
| 256 个填充值均未通过筛选 | 检查原始文件名、编码与所选方案；仍失败时使用真实 Key/IV，并核对派生假设。 |
| 提示 326 或未知版本 | 停止套用 582 算法，保留样本及版本信息用于后续验证。 |

Windows 实机仍需验证 UAC、Wintun 创建与退出、真实 Qt TLS 信任、中文路径、休眠恢复及长视频导出。CI 的模拟测试不安装根证书、不启动 TUN，也不能代替这些验证。ARM64 构建还需要对应设备验证。

本地回归包含 AES 标准测试块、大文件分块与取消、损坏输入、MKV 到 MP4、导入与历史重载，以及使用报告所述 Windows 响应结构的 sing-box 采集测试。Windows x64 CI 增加了这些适配用例；真实系统操作仍由人工验收。
